# Generated maps

## Why this exists

When most of the code is written by a model, the first thing to rot is not code quality, it is knowing what
already exists. Each session the model knows only what it reads; nothing prompts it to look for the concept it is
about to recreate, so it recreates it, locally correct, under a new name. A rules file is advice and ages. A
hand-written architecture doc rots silently and is still trusted. A generated doc with nothing forcing its
regeneration is stale by the second commit.

A map is the fix: **a view of the system generated from the source, committed as a file, and regenerated by a
test that fails when the committed copy differs.** The test is what makes the model's memory trustworthy. The
model is the map's first reader, before it writes; the human reviewer is the second.

## The five rules

1. **Never hand-write a map.** Every map comes from a generator. The only hand-written file is the maps README
   (what each map answers, which ones block).
2. **The test suite is the trigger.** If CI cannot build the project, the suite that gates every commit is the
   pipeline. A red maps test is never a bug in the code under test: the code moved and the map did not.
3. **Informing and blocking are two different kinds of test. Never mix them.** (See below.)
4. **Read the matching map BEFORE adding a concept, and say in the commit message what you found**, even
   "nothing like this exists". The commit line makes a skipped look visible to a reviewer.
5. **Add a map only when a family of bug has shown itself twice.** A map nobody reads is one more thing to
   regenerate.

## Operate: the loop for every change

Do these in this order. The order is the point.

1. **Before writing:** open the map that answers your question (inventory: does this type exist? constants:
   is there already a number for this? dependencies: am I adding an edge or a cycle?).
2. **Make the change.**
3. **Run the maps tests in plain (compare) mode first.** NOT update mode. If you regenerate first, every map
   compares against itself and passes, and the drift is never shown to anyone. This is the single most common
   way the method silently stops working.
4. **Read every failure.** Each one names the map that moved and shows the diff. Ask: is this the move I meant?
   A new edge, a second constant with the same name, a registration missing in one place out of seven?
5. **Only then regenerate** with the project's update command, which should print the full diff of every small
   change (not just a count; a two-line change hides behind a number).
6. **Run the full suite**, then **commit the maps WITH the change** that moved them. In the commit message, say
   what the maps showed.
7. **Review the map diff before the code diff.** It is the architectural summary of the change. An unchanged
   map is information too: that dimension did not move.

If a BLOCKING test fails (step 3), regeneration will not fix it and must not be forced. Change the code, or
use the explicit override and write the reason in the commit.

## Informing vs blocking

**Informing maps** (inventory, dependencies, rules index, constants, project lenses): fail, read, regenerate,
commit. Whatever the code now says becomes the new truth. Their whole value is the attention the diff buys,
and that decays: "regenerate and commit" becomes a reflex within weeks. Treat approval fatigue as the central
risk, not a caveat.

**Blocking tests** do not accept what the code now says:

- **Contracts**, promises made to people outside the project. A persisted-data key that vanished (users'
  saved data silently never read again: additive keys only). A public API member that SHIPPED and vanished or
  changed signature. Compare against a **released snapshot**, recorded at each release cut, never against the
  committed map; otherwise a plain regeneration absorbs the very removal it exists to refuse, and members added
  then withdrawn between releases would be wrongly blocked.
- **Ratchets**, for any property that is monotonic: the set of modules caught in a dependency cycle may not
  grow; the count of bare-number thresholds may only go down. A ratchet holds a BASELINE, not a standard. When
  the count drops, the test asks for the baseline to be lowered in the same commit, so the mess being worked
  off cannot quietly become the target. Raising a baseline is a hand edit with a reason.
- **Overrides** are explicit flags (`ALLOW_SAVE_KEY_REMOVAL`, `ALLOW_API_REMOVAL`), never a regeneration.
- **A contract breaks in both directions.** For data users keep (exports, saves), a field ADDED as required is as
  breaking as a removal: every file the released version wrote now fails to import, and the map shows the change
  as a harmless "+N -0". Guard it too (a field added since the release must be optional, or sit under a new
  optional one), and commit a fixture written by the real old code that must keep importing.

A **decision table** sits between the two: sweep a bounded value (a score, a tier) across its whole range,
call every rule that depends on it, commit the table. It runs the code rather than reading it, so a changed
cell is a changed behaviour. During a refactor the expected diff is NOTHING, which turns "I only moved
declarations" into a checkable claim. Read its diff like a blocking failure.

## Bootstrap: maps on a new project

Smallest useful version, in order; each step is worth having alone. See `references/generator-recipes.md`.

1. **Inventory**: every type by module, with its one-line doc summary. Plus large files.
2. **The test** that regenerates it and compares. Without it you have written another document that will rot.
3. **The update command** that regenerates and prints the diff of short changes.
4. **Contracts next**, before more views: persisted data, public API, wire formats.
5. **Dependencies** (cycles first, then most-used / most-using, then the pairs that use each other) and a
   **rules index** generated from test names (the closest thing to a specification: a behaviour that matters
   is held by a test).
6. **Then one lens per bug family you have actually had twice.** Group the last twenty bug reports; the list
   will be specific to the project. Each generator's header names the incident that justified it.

Generator requirements:

- **Read source syntax, not compiled output** (Roslyn syntax trees, tree-sitter, Python `ast`, TS compiler API).
  No build dependencies needed, and doc comments survive, so a map says what each thing is for.
- **Deterministic output**: stable sort, no timestamps, no absolute paths, no machine-specific content. A noisy
  diff is a diff nobody reads.
- **Skip, don't fail, when the tree is incomplete** (a runner that works from a partial copy). Check for an
  anchor per layer (e.g. `.git` in every repo), never for a runner's name.
- **Each map states its own blind spots in its header** (e.g. "dependencies read from import statements:
  fully qualified names are missed, unused imports counted"). The caveat is part of the map.
- **Line endings: add `.gitattributes` (`* text=auto eol=lf`) BEFORE the first commit**, and compare with line
  endings normalized. On Windows a CRLF checkout against an LF generator turns every map red for no reason.
- **A doc comment belongs to a declaration only if it touches it** (no blank line between). Otherwise the file's
  header comment is silently reported as the doc of its first declaration.
- **Escape what the output format reserves**: a `|` inside a Markdown table cell (`number|null`) breaks the row.
- **No parser in the toolchain** (plain JavaScript, no TypeScript, no npm)? Vendor one parser file for the tools
  only (e.g. acorn), pinned, with its license and the registry integrity checked. It never ships. Guessing
  structure from regexes and names is the fragile detection this skill warns against.
- **For a contract, generate the map by RUNNING the list the code itself validates with** (a field list the
  importer checks against), not by parsing around it. Then the map cannot disagree with the behaviour.
- **Every committed generated file gets the same compare test**, not only maps: a bundled build output, a
  generated client. It rots the same way.
- **Prove each blocking check blocks before trusting it**: on a throwaway copy, remove a released field, add a
  cycle, duplicate a name, and watch both the test and the update command refuse.
- **Before the first release a contract guard protects nothing**: its released snapshot is empty. Say so in the
  map itself ("none yet, so nothing is protected") rather than letting the guard look like protection.
- **Constraints your own build creates are build errors, not maps.** A build that joins modules into one scope
  refuses two top-level declarations with the same name, loudly; a map would only describe the collision.

## When a map is wrong

Watch for two kinds of failure in the maps themselves, and report them when they happen:

- **Name-based detection is wrong in both directions.** Loudly: a misleading name gives a false positive (deltas
  named `...Regard` counted as thresholds; the fix was better names). Silently: something with no telltale name
  is invisible (thresholds compared inline with no constant). Pair every name-based detector with a fact-based
  one (what the code calls, compares, imports, attributes) wherever a fact exists.
- **A map that mixes detection modes labels EVERY line with the mode that produced it** (`(fact)` / `(name)`),
  so a reader knows what to trust.
- **When a map is blind, decide why.** If the CODE is implicit (a human reader would have to guess too), change
  the code: name the constant, type the parameter. If the generator reads badly, fix the generator.

## What maps do not solve

- **The same concept under two names** (`HostileThreshold = -30`, `EnemyLimit = -25`). The map puts them side by
  side; judgement says they are one. That judgement can be delegated to a fresh agent pointed at the maps, told to
  open the source before reporting and to rule each finding "one concept" / "two honest questions" / "needs the
  owner". Expect roughly one real defect in four, and some apparent duplicates that are deliberate (mirrored
  constants with opposite effects: merging them would be the bug).
- **A behaviour that changed with no test changing.** Not a map gap: a missing test.
- **Circularity**: the same model writing code and tests. The external checks are user bug reports quoted in
  the tests they produced, and a human reading the rules diff at each release.
- **Duplication itself.** Maps make it visible; a TYPE makes it impossible (rungs inside the type, `x >= 20`
  refused by the compiler, two scores over the same range no longer interchangeable). A ratchet keeps the gap
  between the two from growing while you migrate, and the decision table proves each migration step moved no
  behaviour.

## A map as a source of proposals

Maps are not only for converging on the existing architecture. When a map shows the same shape repeated in
several places (spawn, steer, never saved, despawn before save, suppress the destroy event: three times), that
is a proposal for a shared service. Say so to the user with the map lines as evidence; do not refactor
unasked.
